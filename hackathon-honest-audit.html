Module-by-module honest status

Module 1 — Skills Signal Engine working

Pipeline: llm-extractor → country-adjuster → scorer → profile. LLM is OpenRouter (openai/gpt-oss-120b:free default), with a deterministic heuristic fallback that runs offline. ESCO/ISCO scoring is rule-based and traceable.

Working well

Auditable scoring weights, country-priority ISCO boost, per-skill match scores, O*NET task evidence, and an explainable match_reason string in the profile.

Real problems

Heuristic fallback only knows ~6 sectors and ~6 skill phrases (phone repair, sewing, etc.) — anything outside that produces an empty signal set when no API key is configured. The 280 MB taxonomy is loaded into RAM at boot and rescanned linearly per request. local_informal_skills.json is referenced but missing on disk, so the "local skills not in ESCO" channel is currently dead.

Module 2 — Automation Risk partial

automationRiskEngine.js resolves a country scenario, picks task multipliers (physical / routine cognitive / non-routine cognitive / social), and returns adjusted_risk = clamp(base_risk × weighted_multiplier + scenario_adjustment).

Working well

Country-calibrated by World Bank income tier, three scenario toggles, uncertainty band, and an inline econometric panel (min wage, broadband, internet, self-employment).

Real problems

The route reads body.occupation.automation_risk_base, but Module 1's profile never emits that field. So unless a caller hand-injects a base risk, every Module 2 call silently falls back to 0.5 — which makes every country look medium-risk regardless of role. This is the highest-impact contract bug.

Module 3 — Opportunities + Dashboard partial

opportunityEngine.js ranks 6 pathway types per country (formal, self, gig, training, microenterprise, agriculture), surfaces real WDI/ILOSTAT/wage signals as a youth_view, and exposes a policymaker_view with priority sectors and labor-market snapshot.

Working well

12+ econometric signals visible to the user (not buried in scoring), normalised pathway weights, country-specific providers (NVTI, MASLOC, BRAC, BTEB, …), and traceable rationale per opportunity.

Real problems

Reads module1Output.skills as an array and module1Output.final_selection as a top-level object — but the actual profile produces skills.mapped (object) and primary_occupation. Pipe Module 1 → Module 3 today and you get zero matched skills, no top occupation, and degraded ranking. Same for adjusted_readiness, which the engine reads but Module 1 never produces.

Config layer (3-layer merge) partial

configLoader.js merges generated base + manual country override + manual automation override + manual opportunity override + i18n. Manual layers always win.

Working well

250 generated country configs, browsable per-country files in config/generated/{countries,automation,opportunities}/, ISO-2 ↔ ISO-3 normalisation, language → translation file resolution.

Real problems

config/countries/ and config/automation/ directories no longer exist on disk — the loaders survive (existsSync checks) but every country gets the generated baseline only. The "GH and BD have rich manual labor-market overrides" story is only half-true today: only config/opportunities/{GH,BD}.json are present.

Frontend missing

The repo has services/node-api/ (the API) and a stale, empty server/ folder. The README claims a client/ Next.js app exists. It does not. There is no React, no Next.js config, no UI page anywhere in the working directory.

Implication: a judge cannot click through Module 1 → Module 2 → Module 3 in a browser today. You can only demonstrate the system via curl/PowerShell/Postman against port 4000, or via the two existing canvases in this workspace. This is the single biggest gap in the project.

Critical contract bugs (these will bite you on stage)

Module 3 reads array, profile emits object silent

opportunityEngine.parseSkillSignals does Array.isArray(module1Output?.skills) ? module1Output.skills : []. But profile.js emits skills: { mapped: [...], local_unmapped: [...] }. Result: skill confidence is averaged from an empty array, defaults to 0.5, and every opportunity scores against zero detected skills.

Fix: either change M3 to read module1Output.skills?.mapped ?? [] and map plain_label / match_score into the engine's expected { name, confidence } shape, or have profile.js additionally emit a top-level skills_flat array.

final_selection vs primary_occupation silent

Module 3's getTopOccupation reads module1Output?.final_selection?.title; the actual profile lives at module1Output?.primary_occupation. Result: top occupation collapses to null and the rationale text loses the ESCO/ISCO line.

Fix: read both keys, or rename one of them. Same applies to adjusted_readiness.automation_risk_adjusted, which Module 3 expects but Module 1 never produces — currently it lands in the silent 0.5 branch of inferAutomationReadiness.

Module 2 has no real base risk source silent

calculateAutomationRisk averages baseRisk, occupation.automation_risk_base, occupation.base_risk, occupation.risk — all of which are absent from a real Module 1 output. The fallback is a hard-coded 0.5.

Fix: ship a small Frey-Osborne table keyed by SOC or ISCO group inside data/processed/, wire it into build-module1-index.mjs, and have profile.js attach automation_risk_base to primary_occupation based on the ISCO/SOC crosswalk that's already in the taxonomy.

How to run / demo it today (no frontend)

Both OPENROUTER_API_KEY and the heuristic fallback work — set the key for a smarter Module 1 skill extraction; leave it unset for fully offline runs.

# one-time data prep
python scripts/fetch-wdi-all-countries.py
node   scripts/build-country-registry.mjs
node   scripts/generate-country-configs.mjs
node   scripts/build-module1-index.mjs

# start the API (port 4000)
cd services/node-api
$env:OPENROUTER_API_KEY = "sk-or-..."   # optional
npm install
npm run dev
# Module 1 - generate a portable skills profile
curl -s http://localhost:4000/api/module1/profile \
  -H "content-type: application/json" \
  -d '{"answers":{
        "work_description":"I repair phones, replace screens and explain problems to customers",
        "country_code":"GH",
        "sector":"technical_services",
        "experience_years":2,
        "education":"upper_secondary",
        "tools":["screwdriver","internet"],
        "selected_skills":["fix phone","customer"]
      }}'

# Module 2 - country-calibrated automation risk
curl -s http://localhost:4000/api/module2/automation-risk \
  -H "content-type: application/json" \
  -d '{"country_code":"GH","scenario":"current",
       "occupation":{"title":"Mobile phone repairer","automation_risk_base":0.42}}'

# Module 3 - opportunities + econometric dashboard
curl -s http://localhost:4000/api/module3/opportunities \
  -H "content-type: application/json" \
  -d '{"country_code":"GH","module1_output":{ /* paste M1 response.profile */ }}'

# Browse the config layer
curl -s http://localhost:4000/api/config/stats
curl -s http://localhost:4000/api/countries
curl -s http://localhost:4000/api/config/GH | jq '.opportunities.types[] | {id, weight}'

What's actually remaining for the hackathon

Ordered by demo impact. Items 1–3 are blockers; 4–6 fix correctness; 7–10 are polish but materially raise the perceived quality bar.

1. Build any frontend at all (React/Next or even a plain HTML page) — you currently have zero UI. This is the single biggest blocker for a demo.
2. Fix the Module 1 → Module 3 output contract: skills is an OBJECT in profile.js but Module 3 reads it as an ARRAY, final_selection.title is read but profile emits primary_occupation.title, adjusted_readiness is read but never produced. Today, piping M1 → M3 silently degrades.
3. Add automation_risk_base to primary_occupation in profile.js (or pull it from a Frey-Osborne lookup) so /api/module2/automation-risk has a real base risk to calibrate, not the silent 0.5 fallback.
4. Recreate config/countries/ and config/automation/ override files for GH and BD. Loaders look for them but they no longer exist on disk — so you have ZERO manual overrides for country labor markets right now, only for opportunity types.
5. Replace the linear scan over all ESCO occupations on every Module 1 request with a sector-bucketed shortlist. The 280 MB taxonomy currently loads into RAM at boot AND is iterated end-to-end per request.
6. Generate placeholder translation files for the top languages (Hindi, Arabic, Swahili, French, Spanish, Portuguese) under config/i18n/ — right now only en.json + bn.json exist, so the "all-country i18n" claim is mostly aspirational.
7. Write a curl/PowerShell demo script that runs all 3 endpoints end-to-end with a known seed input and prints a clean transcript — this is your fallback demo if the frontend isn't ready by judging time.
8. Delete dead artefacts: empty server/routes + server/services dirs, py.py duplicate of fetch-wdi-all-countries.py, and stale README sections that reference a client/ folder that no longer exists.
9. Add at least a smoke test per endpoint (node --test) so the API contract is verified before you demo. Currently zero tests in the repo.
10. Add a minimal API key check on POST routes if the demo is publicly reachable. OpenRouter key is per-server; nothing prevents a malicious caller from burning your quota.
If you only do three things before judging

1. Ship any frontend at all — even a single static HTML page that calls all three endpoints and renders the JSON. The two existing canvases (architecture + this audit) are a solid backup, but a clickable worker-facing flow tells the story 10× faster.

2. Patch the Module 1 → Module 3 contract (one ~30-line change in opportunityEngine.js or profile.js). Without this, your end-to-end pipeline reads as "broken" the moment a judge inspects the JSON.

3. Restore the manual override files for config/countries/{GH,BD}.json and config/automation/{GH,BD}.json. Your "configurable for any country without code changes" claim hangs on these existing.
